## 1. 판단 요약

제공 자료는 운영 장애 대응 AI 에이전트를 중심으로, 개별 설계 패턴을 학습하고 통합한 구성이다. 기존 코드 개선과 신규 주제 개발 모두 가능하다. 현재로서는 기존 기반을 재사용하고 **검색·근거 검증·평가를 강화하는 방향**이 제한된 일정에서 구현 완성도와 개선 효과를 설명하기에 유리하다. 이는 제안이며 프로젝트 주제를 확정한 것은 아니다.

## 5. 구체적인 개선 후보

### A. 검색과 조사 대상

1. **런북 선택이 단일 키워드 분류다.**
   [graph.py:192](/Users/user/mini-project/all_total_vue_student/agent/graph.py:192)에서 알림들을 합친 뒤 먼저 일치하는 유형 하나를 고른다. 결제 CPU 문제와 캐시 메모리 문제를 함께 주면 `cpu-spike` 하나가 선택된다. 유형별 문서 검색, 복수 원인 후보, 시스템별 근거 연결을 추가할 여지가 있다.
2. **알 수 없는 시스템을 auth-service로 치환한다.**
   [graph.py:40](/Users/user/mini-project/all_total_vue_student/agent/graph.py:40)와 모델 계획 보정 코드에 기본 대상이 있다. `billing-service` 요청에서도 다른 시스템을 조사할 수 있으므로 대상 재질문이나 명시적인 미지원 응답이 필요하다.
3. **복수 시스템 중 일부만 계획된 경우 복구가 부족하다.**
   [openai_llm.py:168](/Users/user/mini-project/all_total_vue_student/agent/openai_llm.py:168)의 보정은 research 작업이 0개일 때만 실행된다. 모델이 결제·캐시 중 결제만 계획하면 캐시는 누락된 채 남는다. 계획된 대상과 요청에 등장한 대상을 비교하는 검사가 가능하다.

### B. 검증과 재계획

4. **검증이 사실 정확성을 확인하지 않는다.**
   [graph.py:275](/Users/user/mini-project/all_total_vue_student/agent/graph.py:275)는 30자 이상이고 `1)`가 있으면 합격시킨다. 근거 없는 CPU 999% 주장도 형식을 맞추면 통과했다. 3번째 시도에서는 짧은 답변도 합격으로 바꾼다. 수치 일치·출처 존재·요청 충족을 검사하고, 상한 도달 시 품질 미달 상태를 별도로 표시하는 개선이 가능하다.
5. **재계획의 충분성 판정이 느슨하다.**
   [graph.py:217](/Users/user/mini-project/all_total_vue_student/agent/graph.py:217)는 runbook 항목이 하나라도 있거나 재계획 1회에 도달하면 충분하다고 한다. `Runbook Not Found` 문자열도 runbook 항목으로 들어오면 충분으로 판정됐다. 대상별 조사 완료·문서 유효성·관련성을 확인할 수 있다.
6. **검증 전 초안이 이미 화면에 노출된다.**
   write에서 토큰을 전송한 뒤 validate를 수행한다. 따라서 검증이 최종 상태를 제어하더라도, 반려된 내용은 이미 사용자에게 보일 수 있다. 임시 초안 표시나 검증 완료 후 노출 등 UX 결정을 함께 해야 한다.

### C. 실행·세션·오류 처리

7. **실행 스크립트가 대화 DB를 삭제한다.**
   [로컬 실행 스크립트:61](/Users/user/mini-project/all_total_vue_student/sh/run_agent_ollma.sh:61), [OpenAI 실행 스크립트:52](/Users/user/mini-project/all_total_vue_student/sh/run_agent_openai.sh:52)에 `rm -f session.db`가 있다. 저장소 자체는 영속적이지만 같은 스크립트로 재시작하면 기록이 지워진다. 프런트의 thread ID도 새로고침마다 새로 생성되어 기존 대화에 다시 연결되지 않는다.
8. **OpenAI 답변은 실제 토큰 스트리밍이 아니다.**
   [openai_llm.py](/Users/user/mini-project/all_total_vue_student/agent/openai_llm.py)는 전체 답변을 받은 뒤 콜백을 한 번 호출한다. Ollama의 답변 경로는 비동기 스트리밍을 구현했다. 두 모델의 route/plan/analyze에는 동기 HTTP 호출이 있어 비동기 서버의 동시 요청을 막을 수 있다.
9. **병렬 작업의 실패 격리가 부족하다.**
   research의 `asyncio.gather`에서 한 작업이 예외를 내면 해당 조사 단계가 예외로 종료된다. retry는 모니터링 Tool의 TimeoutError에만 적용된다. 성공한 결과를 살리고 실패한 출처를 표시하는 처리를 추가할 수 있다.
10. **대화 저장과 그래프 재개는 다르다.**
    현재 `g.compile()`에는 체크포인터가 없고 SQLite에는 메시지만 저장한다. 장애 조사 경로는 저장된 history를 상태로 받지만 route/plan/write의 모델 입력에 활용하지 않는다. 사람 승인·중단 후 재개와 “그 서버도 다시 확인해줘” 같은 후속 질문을 지원하려면 추가 설계가 필요하다. v1 SSE 경로에는 메시지 저장도 빠져 있다.

### D. 평가와 데이터

11. **문서가 언급하는 평가 실행기가 배포본에 없다.**
    가이드의 `eval/run_eval.py`, 매뉴얼의 자동 평가·실패 사례 편입 설명에 대응하는 실행 파일이 현재 학생 폴더에서 확인되지 않았다. 제공된 회귀 쿼리는 수동 테스트 입력 목록이다. Capstone의 LangSmith 기본 실습을 참고해 프로젝트용 평가기를 새로 만들 수 있다.
12. **모니터링은 샘플이며 비용 값은 비교용이다.**
    데이터는 시스템 6개의 JSON 기준값에 난수를 더한 형태다. p95·디스크·연결 풀 알림은 문자열에 있지만 구조화 수치나 시계열은 없다. `cost_usd`도 실제 청구액이 아니라 고정 가상 단가로 계산한 비교값이다. 실제 운영 진단이나 실제 비용 절감으로 과장하면 안 된다.

## 6. 추천 범위와 대안

### 우선 제안: 근거를 확인하는 장애 대응 에이전트

핵심 문제를 “증상에 맞는 문서를 찾고, 조사한 사실에 맞게 답변하는가”로 잡는다.

1. 런북·장애 사례를 대상으로 의미 검색을 추가하고 문서 ID·유형·출처를 유지한다.
2. 요청한 시스템의 조사 누락을 검사하고, 미등록 시스템은 확인 질문으로 처리한다.
3. 답변의 수치·출처를 코드로 검사한다. 의미적 요청 충족은 필요할 때 LLM 심판으로 보완한다.
4. 동일 평가셋으로 기존 방식과 비교하고 결과를 저장한다.

모듈화와 의존성 주입은 위 기능을 분리하고 검증하는 범위에서 적용한다. 전문 서브그래프, 사람 승인, 장기 메모리를 동시에 모두 도입하면 평가할 핵심이 흐려지고 일정이 커질 수 있다.

현재 런북은 6개로 짧아 키워드·전문 검색만으로도 충분할 수 있다. RAG 도입 효과를 주장하려면 자연스러운 표현 차이·복합 장애가 있는 평가 질의와 추가 문서를 준비하고 간단한 검색 기준선과 비교해야 한다. 합성 문서는 샘플임을 표시하고, 정답과 질의를 함께 생성해 평가를 쉽게 만드는 편향도 점검한다.

| 방향 | 장점 | 추가 부담 |
| --- | --- | --- |
| 기존 에이전트 개선 | 비교 기준과 샘플 데이터가 있어 개선 효과를 설명하기 쉽다 | 기존 결함과 교육용 장치를 구분해야 한다 |
| 기반 재사용 + 신규 도메인 | API·MCP·그래프 구조를 활용하며 새 사용자 문제를 풀 수 있다 | 데이터 확보, 도구·평가 기준 재설계가 필요하다 |
| 전면 신규 구축 | 목적에 맞게 구조를 자유롭게 정한다 | 통합 기반과 평가 기준을 함께 만들어야 한다 |

신규 프로젝트를 선택하더라도 먼저 사용자·문제·접근 가능한 데이터·성공 기준을 정해야 한다. 현재 자료만으로 신규 도메인을 확정하지는 않았다.

| 런북 검색 | Top-1 정확도, Recall@k, 복수 장애 문서 회수율 |
| 조사 범위 | 요청 시스템 누락률, 미등록 시스템 오치환율 |
| 답변 근거 | 인용 수치 일치율, 출처 연결률, 근거 없는 주장 비율 |
| 검증 | 오류 응답 차단률과 정상 응답 오차단률 |
| 성능 | 전체 시간, 첫 이벤트·첫 답변 토큰 시간, 동시 요청 지연 |
| 자원 | 실제 입력/출력 토큰, 모델 호출 수, 비교용 비용과 실제 비용 구분 |
| 장애 대응 | 부분 실패 시 응답 성공률, 재시도 수, 부족한 근거의 명시 여부 |

평가 입력은 기존 회귀 쿼리 외에 표현이 다른 증상, 복수 시스템, 미등록 대상, 문서 없음, 모순된 수치, 도구 실패를 포함한다. 개발에 사용하지 않은 질의를 별도로 두고 모델·데이터·설정을 고정해 여러 번 측정한다.

비교 시 주의할 교육용 장치:

- research 작업마다 `asyncio.sleep(0.35)`가 있다.
- MCP 최초 모니터링 호출에는 의도적인 타임아웃이 있다.
- 모니터링 값에는 임의 변동이 있다.
- fake 모델은 불필요한 분석 작업과 저품질 1차 초안을 의도적으로 만든다.
- fake 모델은 실제 모델과 대상 추출·분석 동작이 같지 않다.

이 조건들은 양쪽에 동일하게 적용하거나 실험 설정으로 분리해야 한다. v1/v2는 여러 기능이 동시에 달라지므로 단일 개선 효과를 입증하는 비교에는 적합하지 않다. 원본 v2와 해당 기능만 변경한 v2를 비교하는 편이 원인을 설명하기 쉽다.

## 8. 이번 확인 범위

- 가이드 PDF 전체 텍스트와 주요 요구·평가 페이지의 화면을 확인했다.
- Capstone PDF의 구성·설계·관련 개념, 실습 설명과 개선 예제를 대조했다.
- 학생 코드의 API, 그래프, 모델 어댑터, MCP, 저장소, 화면, 실행 스크립트와 데이터를 검토했다.
- 외부 패키지·네트워크를 제외하고 원본 함수/클래스를 AST로 추출하여 기본 대상 치환, 복합 장애 단일 유형 선택, 검증 오통과, 없는 런북의 충분 판정, 계획 일부 누락을 재현했다. 모델 계획 누락은 가짜 모델 응답을 주입한 조건부 재현이며 실제 모델 발생률 측정이 아니다.
- 통합 서버 기동, 실제 모델 호출, LangSmith 전송과 성능 측정은 수행하지 않았다. 통합 동작 완료를 확인한 분석은 아니다.
- 원본 코드와 학습 자료는 변경하지 않았으며 이 분석 문서만 추가했다.
