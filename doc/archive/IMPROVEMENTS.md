# 기존 운영 장애 대응 에이전트: 1차 개선

> 이 문서는 1차 개선 당시의 기록입니다. 현재는 OpenAI·Ollama 실제 연결과 RAG를 추가했습니다.
> 최신 구조·실행 방법·실측 결과는 [실제 모델과 RAG 개선 설명](/Users/user/mini-project/all_total_vue_student/doc/archive/RAG_REAL_MODELS.md)을 참고하세요.

## 어떤 프로젝트인가

운영 담당자가 서비스 이상 증상을 입력하면, 에이전트가 조사 계획을 세우고 모니터링 수치와 대응 매뉴얼을 조회해 권장 절차를 안내하는 웹 채팅 서비스다.

예: `payments-service CPU 급증 원인을 진단해줘`

처리 흐름은 요청 분류 → 조사 계획 → 불필요한 작업 제거 → MCP 모니터링 조회 → 대응 매뉴얼 보강 → 필요 시 비교 분석 → 답변 작성 → 검증·재작성 → 결과 안내다. 조사 진행 상황은 화면에 순서대로 나타난다.

현재 데이터는 시스템 6개와 런북 6개의 샘플이다. 재시작·삭제·롤백 등 실제 운영 조치를 실행하는 기능은 없고 절차만 안내한다.

## 바로 확인하기

이 폴더에서 실행한다.

```bash
bash sh/run_demo.sh
```

브라우저: [http://localhost:8600](http://localhost:8600)

전용 `.venv`에 패키지를 설치해두었다. 다른 환경에서는 `sh/setup_venv.sh`로 환경을 준비할 수 있고, 이번 검증 환경의 패키지 버전은 `requirements.lock.txt`에 기록했다.

데모 모드는 **fake LLM의 규칙 기반 응답**을 사용한다. FastAPI, LangGraph, MCP subprocess, SQLite, Vue 화면은 실제로 실행된다. API 키가 필요하지 않으며 데모 스크립트는 LangSmith 전송을 끈다. 실제 LLM의 자연어 이해 능력이나 품질을 확인한 데모는 아니다.

직접 입력해볼 예시:

- `payments-service CPU 급증 원인을 진단해줘`
- `cache-service 메모리 사용률이 계속 올라가요`
- `payments-service랑 cache-service 둘 다 저하됐는데 공통 원인을 분석해줘`
- `제 이름은 민수입니다` → 새로고침 → `제 이름이 뭐였죠?`

모니터링 값은 조회마다 조금씩 달라진다. 종료는 실행한 터미널에서 Ctrl+C로 한다. 8100·8600 포트를 사용 중이면 새 데모를 중복 기동하지 않는다.

## 이번에 개선한 기존 동작

| 항목 | 기존 | 개선 |
| --- | --- | --- |
| 답변 검증 | 길이·번호만 검사 | CPU·메모리 인용 수치를 수집 결과와 추가 대조 |
| 검증 상한 | 3회째 실패도 합격 처리 | 실패를 유지하고 원본 모니터링 정보만 반환 |
| 초안 노출 | 검증 전에 초안이 화면에 전송됨 | 장애 답변은 검증 후 최종 결과만 노출 |
| 문서 충분성 | 없는 런북 응답도 충분하다고 판단 | 빈 문서·Not Found를 배제하고 상한 도달을 별도로 표시 |
| 재시작 | 모델 실행 스크립트가 대화 DB 삭제 | 기존 SQLite 기록 유지 |
| 새로고침 | 매번 새 대화 ID 생성 | 같은 브라우저에서 기존 대화 ID 유지 |
| v1 스트리밍 | 대화 저장 누락 | 일반 API와 같이 메시지 저장 |
| 데모 동작 | 일부 기존 장애 질문을 인사로 처리, 불필요한 web-01 자동 조사 | 증상 표현 인식 보완, 요청 대상 중심 조사 |
| 화면 안내 | fake도 실모델이라고 표시 | 샘플·규칙 기반 모드를 명시하고 연결 실패 안내 |

새로고침 후 이전 말풍선을 다시 그리는 기능은 추가하지 않았다. 서버의 대화 이력을 같은 ID로 계속 사용하는 방식이다.

## 검증 결과

```bash
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python eval/compare_validation.py
```

- 자동 검사 16개 통과. 원본 수치 대조, 시스템 간 수치 혼동, 검증 상한, 부적절한 초안 비노출, 문서 없음, 메시지 보존 등을 확인했다.
- 실제 MCP subprocess를 사용해 일반 응답·SSE 완료·v1 재기동 후 메시지 복원을 확인했다.
- 브라우저에서 조사·재작성·검증 흐름 및 새로고침 후 이름 기억을 확인했다.
- 동일한 고정 사례 10개에서 검증기의 올바른 판정은 기존 4/10 → 개선 10/10이었다. 기존 기준은 변경 전 `graph.py`의 길이·번호·상한 처리 로직을 재현했다.
- 평가 입력과 결과는 `eval/validation_cases.json`, `eval/validation_results.json`에 있다. 수동 사례를 사용한 회귀 평가이며 실제 모델 전체 정확도를 의미하지 않는다.

## 한계와 트레이드오프

- 검증기는 정해진 자연어 표현의 CPU·메모리 백분율을 확인한다. 모든 문장·지표·인과관계의 진위를 검증하지 않는다. 시스템이 앞에 명시되지 않은 수치는 조사한 시스템들의 값 중 존재하는지 확인하는 수준이다.
- 런북의 조건부 백분율은 문서에 등장한 값인지 확인해 현재 측정값과 구분한다. 문장 의미를 완전히 분석하는 방식은 아니다.
- 근거가 있는 수치라도 그로부터 도출한 원인·조치의 타당성은 별도 검토가 필요하다.
- 장애 답변은 검증을 기다리므로 첫 답변 글자가 표시되는 시간이 늦어질 수 있다. 조사·작성·검증의 진행 이벤트는 계속 전달한다. 일반 대화의 스트리밍 경로는 유지했다.
- 런북 선택은 기존 단일 키워드 방식이다. 복합 장애별 복수 검색, RAG, 미등록 대상 재질문, 실제 모니터링 연동은 이번 범위에 포함하지 않았다.
- 실제 OpenAI/Ollama 호출은 실행하지 않았다. OpenAI의 토큰 스트리밍 부재와 모델 호출의 동기 처리도 남아 있다.
- 도메인, 기본 화면 구성, MCP·LangGraph 구조를 유지한 1차 개선이다. 신규 서비스 기능은 이후 별도 범위로 결정한다.
