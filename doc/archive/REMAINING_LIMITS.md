## 1. 모니터링: 실제 값과 샘플을 구분

기본 `MONITORING_BACKEND=hybrid`에서는 다음 대상을 사용할 수 있습니다.

- `auth-service`, `web-01`, `payments-service`, `cache-service`, `gateway-service`, `log-service`: 기존 학습용 샘플입니다.
- `local-host`: 이 프로그램을 실행하는 PC의 실제 사용률입니다. `psutil`로 CPU를 짧은 구간 동안 측정하고 메모리·디스크를 함께 읽습니다.

데이터에 `data_origin`과 측정 시간을 붙입니다. 화면의 답변 하단에도 `sample`, `local`, `prometheus`를 구분합니다. 최근 5회 측정은 응답에 포함하고, 최대 10,000개의 스냅샷을 SQLite에 보관합니다. 지속 수집기가 아니라 요청할 때 측정하므로 장기간 추세 분석을 위한 시계열 서버를 대체하지 않습니다.

예: **“local-host의 CPU와 메모리 상태를 확인하고 이상 여부를 진단해줘”**

### 회사 서버를 붙이는 방법

1. `data/monitoring_sources.example.json`을 별도 설정 파일로 복사합니다.
2. 대상 이름과 실제 서버에 맞는 PromQL을 지정합니다. 예시의 `YOUR_HOST:9100`은 교체해야 합니다.
3. `.env`에 `MONITORING_SOURCES_PATH`, `PROMETHEUS_URL`을 설정합니다. 인증이 필요하면 `PROMETHEUS_TOKEN`을 사용합니다.
4. 서버를 재시작합니다. `MONITORING_BACKEND=prometheus`이면 샘플과 로컬 대상을 제외합니다.

필수 쿼리는 `up`, `cpu_percent`, `memory_percent`입니다. 사용률은 0~100, `up`은 0 또는 1이어야 합니다. 각 쿼리는 한 개의 최신 시계열을 반환해야 합니다. 값이 없거나 여러 개이거나, NaN·오래된 값이면 실패로 처리하며 샘플이나 0으로 대체하지 않습니다.

현재 사용자의 운영 서버 주소는 제공되지 않았습니다. Prometheus 연결부는 모의 HTTP 응답으로 검증했으며 실제 운영 서버 연결 완료를 의미하지 않습니다. 예시 PromQL은 Linux node_exporter 형식이므로 다른 수집기는 쿼리를 조정해야 합니다.

## 2. 답변: 조치의 조건을 지키고 의미도 검토

이전에는 모델이 매뉴얼을 요약하면서 “특정 배포 직후라면 롤백”을 “롤백”으로 줄일 수 있었습니다.

현재는 다음 순서로 처리합니다.

```text
관측값과 관련 매뉴얼 수집
 → 모델이 원인 후보 + 원문 단계 ID 선택
 → 코드가 측정값과 선택한 원문을 그대로 조립
 → 수치·출처 검사
 → 의미 검증
 → 합격한 답변만 공개
```

원문 단계는 조건과 함께 보존합니다. 선택 목록에 없는 단계는 거부합니다. CPU·메모리·디스크 수치와 출처를 대조하고, 힙 사용률을 시스템 메모리 사용률로 대체하는 표현은 반려합니다. 원인 후보에 정량 수치를 재생성하지 않도록 제한했습니다.

의미 검증은 근거 없는 원인 단정, 다른 지표의 혼용, 관측 대상 누락, 명백히 무관한 조치를 검토합니다. 원인을 확정할 수 없어서 가설로 표현한 것은 허용합니다. 실제 OpenAI 시험에서 이 표현을 과도하게 반려하는 사례가 있어 검증 지침을 보정했습니다.

3회까지 실패하면 합격으로 바꾸지 않고 확인된 관측값만 안내합니다. 의미 검증기도 모델이므로 오판 가능성은 남습니다. 매뉴얼 자체의 내용이 올바른지 검토하고 최종 조치는 운영 담당자가 판단해야 합니다. 프로그램은 실제 재시작·롤백·파일 삭제를 실행하지 않습니다.

## 3. 검색: 같은 시스템의 여러 증상도 수집

“payments-service에서 CPU 급증과 메모리 누수가 함께 발생”하면 CPU와 메모리 검색을 각각 실행하고 중복을 제거합니다. 여러 시스템이면 다른 시스템의 증상을 뒤섞지 않도록 대상별 요청 구간과 해당 관측 알림을 사용합니다.

`RAG_TOP_K`는 증상별 상위 청크 수입니다. 최대 4개 증상 질의, 최대 5개 중복 제거 청크를 사용합니다. `RAG_MIN_SCORE=0.35` 미만은 제외합니다. 단계 번호·제목을 기준으로 문서를 나누며 한 조치의 조건을 중간에서 자르지 않습니다.

이 임계값은 현재 모델·자료에 대한 설정값입니다. 다른 임베딩 모델이나 회사 문서에 적용할 때 다시 평가해야 합니다. 증상 분리 규칙은 보조 정책이며 모든 자연어·관계 표현을 이해하지는 않습니다. 문서 수가 커지면 전용 벡터 인덱스, 랭킹 평가, 문맥 길이 관리가 추가로 필요합니다.

## 4. 기록과 복구: 새로고침과 프로세스 재시작을 구분

- 새로고침: 같은 대화 ID로 저장된 말풍선·출처·사용량을 복원합니다. 100개 이전 메시지는 ‘이전 대화 더 보기’로 불러옵니다.
- 후속 질문: “그 서버 다시 확인”은 직전 조사 대상이 하나일 때만 연결합니다. 이전 대상이 여러 개면 이름을 확인합니다. 시스템을 특정할 수 없으면 임의로 골라 조회하지 않습니다.
- 긴 대화: 전체 원문은 DB에 남기고 모델에는 최근 대화와 길이 제한을 적용합니다. 복잡한 장기 기억 요약 기능은 아닙니다.
- 조사 실패·중단: LangGraph가 완료한 노드의 상태를 `session.db.checkpoints.db`에 저장합니다. 화면의 ‘이어서 실행’으로 미완료 단계부터 재개합니다.
- 다시 진행할 필요가 없는 요청: ‘종료’를 누르면 새 요청을 할 수 있습니다.

복구를 눌러야 모델 호출이 재개됩니다. 실패한 노드에서 응답을 받았지만 체크포인트 저장 전에 중단된 호출은 재실행될 수 있습니다. 따라서 외부 호출의 정확히 한 번 실행이나 중복 과금 방지를 보장하지 않습니다. 복구한 보고서의 측정 시간은 저장된 관측 시점입니다. 새로운 현재 상태가 필요하면 새 요청으로 조회해야 합니다. 복구 동안 같은 대화의 요청은 순차 실행됩니다.

## 5. 호출과 비용

OpenAI는 최대 4개, Ollama 채팅은 최대 1개 동시 호출입니다. 429·502·503·504와 일시적 네트워크 오류는 최대 3회 시도합니다. 토큰을 이미 전달한 스트림은 중복 출력을 막기 위해 자동 재시도하지 않습니다. 대기·재시도·응답을 합한 호출 제한은 `MODEL_DEADLINE_SECONDS=300`초입니다.

OpenAI 금액은 기본적으로 미산정입니다. 필요하면 아래처럼 실제 사용할 모델의 단가를 `.env`에 입력합니다. **아래 숫자는 계산 형식 예시이며 실제 가격이 아닙니다.** 단위는 USD / 100만 토큰입니다.

```dotenv
MODEL_PRICES_JSON='{"YOUR_MODEL":{"input_per_million":1.0,"output_per_million":2.0}}'
```

이 값은 캐시 할인·임베딩 비용·세금 등을 제외한 추정입니다. Ollama는 외부 API 호출료를 0으로 기록하며 PC 장비·전력 비용은 포함하지 않습니다. 데모 토큰은 모의 추정이라는 표시를 붙이고 금액을 계산하지 않습니다.

## 7. 재현 방법과 검증 범위

```bash
# 외부 모델 호출 없는 검사: 실제 MCP 프로세스와 임시 SQLite 사용
.venv/bin/python -m unittest discover -s tests -q

# 실제 OpenAI·Ollama·임베딩·전체 진단: API 사용료 발생 가능
.venv/bin/python scripts/verify_live.py --full

# 실제 로컬 임베딩 검색 평가
.venv/bin/python scripts/verify_live.py --retrieval-eval
.venv/bin/python scripts/verify_live.py --extended-retrieval-eval

# 실행
bash sh/run_live.sh
```

브라우저에서 실제 `local-host` 진단, 새로고침 후 말풍선·출처·토큰 복원, “그 서버 다시 확인해줘”가 같은 대상을 재조회하는 동작을 확인했습니다. 기존 대화는 삭제하지 않고 이전 버전 기록으로 표시합니다.

자동 검사 **42개**를 통과했습니다. 실제 복수 시스템 진단은 OpenAI·Ollama 모두 의미 검증까지 1회에 통과했습니다. 해당 1회 처리 시간은 OpenAI 약 8.2초, Ollama 약 32.1초였으며 평균·속도 개선 보장값은 아닙니다. 서버 재시작 후 복구, 대화 중복 저장 방지, 완료된 분류 단계 재호출 방지, 화면 복원용 출처 저장도 포함합니다.

실제 검색 회귀 사례는 기존 **12/12**, 복합 증상 4개와 무관/미등록 주제 4개를 추가한 **8/8**이 기대한 문서 목록과 일치했습니다. 작고 수동 작성한 조정용 사례이며 독립적인 운영 정확도 평가가 아닙니다. 평가 결과와 실제 모델 기록은 `eval/retrieval_results.json`, `eval/extended_retrieval_results.json`, `eval/live_verification.json`에 있습니다.

아직 남은 실제 의존성은 **운영 서버 주소·수집기·올바른 PromQL·운영 매뉴얼·현장 평가 데이터**입니다. 로컬 측정과 연결 코드가 준비된 상태이며, 이 자료 없이 회사 시스템 연결이나 운영 품질을 확인했다고 표현할 수는 없습니다. 다중 사용자 인증·권한·운영 배포는 현재 로컬 실습 범위를 넘어 별도 구성이 필요합니다.
